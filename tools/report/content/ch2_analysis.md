## 2.2 Варианты решения и выбор наилучшего

Требования технического задания допускают несколько способов построения системы. Варианты рассмотрены по четырем вопросам, от которых зависит архитектура: способ реализации клиентской части, организация хранения данных и обмена ими, структура серверной части и место выполнения алгоритмов машинного обучения.

### 2.2.1 Способ реализации клиентской части

Рассмотрены три варианта: нативное приложение для платформы Android, кроссплатформенное приложение на едином коде для Android и iOS и веб-приложение, устанавливаемое на устройство (прогрессивное веб-приложение). Веб-приложение проигрывает по главным для системы свойствам: возможности хранения зашифрованных данных и фоновой работы в браузере ограничены, а распознавание чеков и речи без подключения к сети недоступно. Кроссплатформенное приложение упростило бы выпуск версии для iOS, однако доступ к средствам платформы в нем выполняется через промежуточный слой, что увеличивает размер приложения и время запуска на бюджетных устройствах, которые составляют основу парка смартфонов целевой аудитории. Кроме того, техническое задание прямо устанавливает язык Kotlin и библиотеку Jetpack Compose. Выбран первый вариант – нативное приложение для Android. Расширение на другие платформы, предусмотренное как перспектива развития, обеспечивается тем, что вся прикладная логика, общая для платформ, сосредоточена на сервере и доступна через программный интерфейс.

### 2.2.2 Организация хранения данных и обмена ими

Рассмотрены три варианта:

- «тонкий» клиент – все данные хранятся на сервере, мобильное приложение запрашивает их при каждом открытии экрана;
- локальное приложение без серверной части – все данные хранятся только на устройстве;
- локальная база данных как основной источник данных приложения с последующей синхронизацией с сервером.

Первый вариант прост в реализации, но противоречит требованию п. 4.1.3.1 ТЗ: базовые функции учета должны выполняться без подключения к серверной части. По результатам опроса работа без подключения к сети Интернет важна для 84 % респондентов, поэтому это требование отнесено к обязательным. Второй вариант обеспечивает автономность, но не позволяет работать с данными на нескольких устройствах, восстанавливать их при утере смартфона и использовать серверные функции – импорт выписок, получение котировок, обучение моделей на обезличенных данных многих пользователей.

Выбран третий вариант. Мобильное приложение записывает каждое изменение сначала в локальную базу данных, поэтому интерфейс не зависит от состояния сети, а введенные данные не теряются при аварийном завершении приложения (п. 4.4.3, 4.4.8.4 ТЗ). Одновременно изменение помещается в очередь несинхронизированных операций, которая передается на сервер при появлении подключения.

Для разрешения конфликтов при синхронизации рассмотрены три подхода: побеждает последнее по времени изменение записи; объединение изменений на уровне отдельных полей; специальные структуры данных с автоматическим слиянием. Данные каждого пользователя изменяет только он сам, а конфликт возможен лишь при одновременной работе на двух его устройствах, одно из которых не подключено к сети. Для такого случая достаточно первого подхода: он прост, предсказуем для пользователя и не требует хранения истории изменений каждого поля. Дублирование операций при обрыве связи исключается уникальным идентификатором операции: повторно присланная операция сервером не применяется.

Рассмотрены три варианта: единое серверное приложение, включающее все функции; набор микросервисов по числу подсистем; модульное серверное приложение с выделенными сервисом машинного обучения и исполнителем фоновых задач. Сравнение вариантов приведено в таблице {tab:server_variants}.

Микросервисная структура избыточна для системы с нагрузкой порядка 100 одновременных пользователей и одним разработчиком: она потребовала бы распределенных транзакций там, где техническое задание предписывает единую базу данных. Единое приложение не разделяет ресурсоемкое обучение модели и обработку запросов и не задает границы, через которую в сервис машинного обучения попадают только обезличенные данные. Выбран третий вариант: серверное приложение, разделенное на модули по подсистемам, отдельный сервис машинного обучения с внутренним программным интерфейсом и исполнитель фоновых задач, получающий задания через очередь (п. 4.1.2.2 ТЗ).

### 2.2.4 Место выполнения алгоритмов машинного обучения

Автоматическая категоризация и прогнозирование могут выполняться на устройстве либо на сервере. Обучение модели категоризации требует обезличенных данных многих пользователей (п. 4.2.1.5 ТЗ) и вычислительных ресурсов, поэтому выполняется на сервере. Применение модели также размещено на сервере: это позволяет заменять версию модели без обновления мобильного приложения и контролировать ее качество. Чтобы категоризация оставалась доступной в автономном режиме, мобильное приложение использует собственную историю пользователя – категорию его последней операции с тем же описанием; этот способ не требует модели и согласуется с формулировкой п. 4.2.1.1 ТЗ «на основе ранее выполненных операций пользователя». Операция, введенная без категории и без подходящей истории, получает категорию от модели при синхронизации. Распознавание текста на фотографии чека и распознавание речи выполняются на устройстве средствами платформы, а разбор распознанного текста – и на устройстве, и на сервере.

### 2.2.5 Выбранное решение

По итогам сравнения принято следующее решение: нативное мобильное приложение для Android с локальной зашифрованной базой данных и очередью операций; серверная часть в составе модульного серверного приложения, сервиса машинного обучения и исполнителя фоновых задач с единой реляционной базой данных; синхронизация по принципу «побеждает последнее изменение» с защитой от повторного применения операций; обучение и применение модели категоризации на сервере с резервным способом категоризации по истории пользователя на устройстве.

## 2.3 Обоснование архитектуры системы

Система построена по клиент-серверной архитектуре с тремя уровнями: клиентский уровень – мобильное приложение; уровень приложений – серверное приложение, сервис машинного обучения и исполнитель фоновых задач; уровень данных – реляционная СУБД, сервер кеширования и очередей, хранилище файлов. Такое разделение прямо следует из п. 4.1.1.9 ТЗ и позволяет развивать и масштабировать уровни независимо.

Мобильное приложение организовано по слоям: слой представления (экраны и модели представления), слой данных (репозитории, локальная база данных, сетевой клиент, модуль синхронизации) и слой предметной логики (расчеты бюджета и целей, разбор текста чека и голосовой фразы). Экраны получают данные только из локальной базы данных; сетевые запросы выполняет модуль синхронизации и те разделы, которые по своей природе требуют сервера – отчеты за произвольный период, рекомендации, портфель с актуальными котировками, административные экраны. Благодаря этому базовые функции учета не зависят от доступности сервера (п. 4.2.4.2 ТЗ).

Серверное приложение разделено на три слоя: программный интерфейс (маршруты REST), бизнес-логика подсистем и инфраструктура (модели данных, сеансы базы данных, безопасность, аудит). Принципиальным решением является единый модуль правил сохранения данных: и запросы программного интерфейса, и операции, принятые при синхронизации из автономного режима, проходят через одни и те же функции. Поэтому проверки вводимых данных, бизнес-правила (например, запрет изменения сделки по истечении 7 дней или режим просмотра для достигнутой цели), автоматическая категоризация, контроль бюджета и запись в журнал аудита выполняются одинаково независимо от того, каким путем поступило изменение.

Для синхронизации каждой записи пользователя присваивается номер ревизии. Счетчик ревизий хранится в учетной записи и увеличивается атомарно одной операцией базы данных, поэтому изменения, сделанные одновременно с разных устройств, получают разные номера. Мобильное приложение запоминает последнюю полученную ревизию и запрашивает только записи с большим номером, что сокращает объем обмена.

Требования безопасности (п. 4.4.4, 4.4.7 ТЗ) учтены в архитектуре следующим образом:

- обмен данными между мобильным приложением и сервером выполняется только по протоколу HTTPS; сертификат TLS устанавливается на обратном прокси перед серверным приложением;
- пароли хранятся в виде результата необратимого хеширования с солью по алгоритму Argon2, одноразовые и обновляемые токены – в виде хеша;
- доступ к программному интерфейсу предоставляется по подписанному токену JWT, права проверяются по роли пользователя на каждом запросе к административным маршрутам;
- локальная база данных мобильного приложения шифруется алгоритмом AES-256, ключ шифрования и токены доступа хранятся в защищенном хранилище Android Keystore;
- сервис машинного обучения не имеет доступа к базе данных и получает только тексты операций без идентификаторов пользователей, сумм и дат;
- вход блокируется на 15 минут после пяти неудачных попыток подряд, все события входа и изменения данных записываются в журналы.

Надежность (п. 4.4.3 ТЗ) обеспечивается немедленным сохранением вводимых данных в локальной базе данных, повторной отправкой очереди операций после сетевого сбоя без дублирования, использованием транзакций базы данных на сервере, ежедневным резервным копированием и резервным узлом базы данных. Серверное приложение не хранит состояние сеансов в памяти, поэтому при росте нагрузки может быть запущено в нескольких экземплярах за общим балансировщиком (п. 4.1.6.2, 4.2.3.2 ТЗ).

| Тестирование | pytest, Locust; JUnit, Robolectric | автоматические тесты серверной части и нагрузочное тестирование; тесты мобильного приложения без устройства |
| Контроль версий и стиля | Git, ruff, Android Lint | единый стиль кода, проверяемый статическими анализаторами (п. 4.3.4.3.5 ТЗ) |

Веб-фреймворк FastAPI выбран в сравнении с Django и Flask. Django включает собственные средства работы с базой данных и административный интерфейс, которые в системе не используются, а описание программного интерфейса требует дополнительных библиотек. Flask не содержит средств проверки входных данных и формирования документации. FastAPI решает обе задачи: каждая схема запроса и ответа одновременно служит правилом проверки данных и частью спецификации OpenAPI, по которой разрабатывался сетевой слой мобильного приложения.

СУБД PostgreSQL выбрана в сравнении с MySQL и документной СУБД MongoDB. Данные системы – счета, операции, бюджеты, цели – тесно связаны между собой и требуют целостности при одновременных изменениях, поэтому документная модель не имеет преимуществ. По сравнению с MySQL PostgreSQL предоставляет более полную поддержку типа точных десятичных чисел и возврат измененных значений в одной операции, на котором основан счетчик ревизий синхронизации.

Для автоматической категоризации выбрана логистическая регрессия по признакам TF-IDF, построенным на символьных n-граммах текста операции. Описания операций в банковских выписках представляют собой короткие строки с названием торговой точки в разных написаниях – в верхнем регистре, латиницей, со служебными суффиксами. Символьные n-граммы устойчивы к таким вариациям, а линейная модель обучается за секунды, не требует графического ускорителя и возвращает вероятность, по которой отбрасываются неуверенные ответы. Нейросетевые модели для этой задачи избыточны: при объеме обучающей выборки в несколько тысяч строк они не дают выигрыша в точности, но существенно усложняют развертывание.

Для прогнозирования расходов и доходов применены скользящее среднее и экспоненциальное сглаживание, в том числе с учетом сезонности (метод Хольта – Уинтерса), как установлено п. 4.3.1.2 ТЗ. Метод выбирается автоматически по длине истории: сезонная модель требует не менее двух полных лет наблюдений, простое сглаживание – не менее четырех месяцев.

Диаграммы архитектуры и структуры программного обеспечения подготовлены в нотациях ArchiMate [@archimate], SysML [@sysml] и UML [@uml].
