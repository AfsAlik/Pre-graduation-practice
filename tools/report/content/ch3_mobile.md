### 3.2.4 Структура мобильного приложения

Мобильное приложение разработано на языке Kotlin [@kotlin] для операционной системы Android версии 8.0 (API 26) и выше. Приложение состоит из одной активности MainActivity, внутри которой экраны строятся средствами Jetpack Compose [@compose] и переключаются библиотекой Navigation Compose. Структура приложения показана на диаграмме компонентов на рисунке {fig:components_mobile}.

!figure components_mobile | assets/diagrams/uml_components_mobile.png | Диаграмма компонентов мобильного приложения | 16.5

Приложение построено по многоуровневой схеме. Верхний уровень образуют экраны и модели представления (ViewModel). Каждый экран состоит из двух функций: функция с окончанием Route получает состояние из модели представления и передает ей действия пользователя, а функция с окончанием Screen только отображает переданное состояние. Модели представления обращаются к репозиториям пакета data.repo и к расчетным модулям пакета domain. Репозитории, в свою очередь, работают с локальной базой данных (пакет data.local), очередью синхронизации (пакет data.sync) и программным интерфейсом сервера (пакет data.remote).

Основной принцип построения приложения – приоритет локальных данных. Единственным источником данных для экранов учета служит локальная база данных: все изменения сначала записываются в нее и в очередь синхронизации, а затем в фоновом режиме передаются серверу. Показатели главного экрана, отчетов, исполнения бюджета, прогресса целей, стоимости и доходности портфеля рассчитываются на устройстве модулями пакета domain по тем же правилам, что и на сервере (п. 3.4.3, 3.4.4). Для этого репозиторий FinanceRepository формирует согласованный срез учетных данных – счета, категории, операции, лимиты, цели, накопления, сделки, последние известные цены и курсы валют – и обновляет его при любом изменении локальной базы данных; все экраны строят свое состояние по одному срезу, поэтому показатели на разных экранах не расходятся. Только через сервер выполняются функции, которым нужны данные или вычисления серверной части: загрузка котировок и курсов валют, рекомендации, прогноз и оценка рисков, импорт выписок и экспорт отчетов в файлы, а также разделы административного модуля. Ответы сервера сохраняются в локальной базе данных и при отсутствии связи показываются с указанием даты их получения.

Объекты приложения создаются и связываются контейнером зависимостей di.AppContainer без использования специальных библиотек. Контейнер создается один раз при запуске процесса; параметры его конструктора позволяют подменять в автоматизированных тестах шифрование, базу данных и источник сведений о сети. Каркас экрана AppScaffold, общий для всех разделов, содержит заголовок с кнопкой возврата, постоянно отображаемый индикатор синхронизации, область всплывающих сообщений о результате действий и нижнюю панель навигации с пятью разделами: «Главная», «Транзакции», «Бюджет», «Цели», «Инвестиции». Остальные разделы открываются из бокового меню главного экрана; пункт «Администрирование» показывается в нем только пользователям с ролью «Аналитик» или «Администратор».

Локальная база данных создается библиотекой Room [@room] и содержит 13 таблиц, перечисленных в таблице {tab:mobile_tables}. Первые девять таблиц соответствуют одноименным таблицам серверной части и имеют общий набор служебных полей, описанный в п. 3.3.1: идентификатор UUID, время создания, изменения и удаления, номер ревизии сервера (нулевой номер означает, что запись еще не подтверждена сервером). Классы этих таблиц одновременно описывают формат JSON, в котором записи передаются при синхронизации. Денежные суммы хранятся текстом в виде точных десятичных чисел, что исключает ошибки округления.

Клиентская часть синхронизации реализована в пакете data.sync. Класс SyncQueue записывает изменение и операцию очереди в одной транзакции базы данных; каждой операции присваивается новый идентификатор op_id, а неотправленная операция с той же записью при этом заменяется, поскольку серверу достаточно последнего состояния записи. Класс SyncEngine выполняет сеанс обмена, протокол которого описан в п. 3.2.3: очередь отправляется частями не более чем по 500 операций, причем счета и категории передаются раньше записей, которые на них ссылаются. Операция удаляется из очереди только после того, как сервер вернул по ней результат, поэтому при обрыве связи она будет отправлена повторно с тем же op_id и не создаст дубликата. Изменения, полученные от сервера, не перезаписывают локальную запись, по которой в очереди уже появилась новая операция. Если по операции получен результат «conflict» или «rejected», действует версия сервера; когда ее нет среди полученных изменений, выполняется полная сверка – загрузка всех записей пользователя с удалением локальных записей, которых нет на сервере. О непринятых операциях пользователь получает сообщение с указанием причины, а событие записывается в журнал ошибок.

Класс SyncManager запускает сеанс синхронизации после каждого изменения данных, при восстановлении подключения к сети и по нажатию на индикатор синхронизации; одновременно выполняется не более одного сеанса. Когда приложение закрыто или сети нет, синхронизацию выполняет фоновая задача SyncWorker библиотеки WorkManager [@workmanager]: разовая задача ставится в очередь с условием наличия сети, периодическая выполняется раз в 15 минут (минимальный интервал WorkManager). После успешного сеанса обновляются профиль, курсы валют и уведомления сервера, на сервер передается журнал ошибок, а из корзины окончательно удаляются транзакции старше 30 дней. Индикатор синхронизации отображает одно из состояний: «Онлайн · синхронизировано», «Онлайн · синхронизация…», «Онлайн · ожидает N операций», «Офлайн · данные сохранены на устройстве» или «Офлайн · ожидает N операций», «Технические работы · …» (сервер в режиме технического обслуживания), «Онлайн · ошибка синхронизации». Состояние передается не только цветом, но и значком и текстом, а его изменения объявляются программам экранного доступа.

Данные на устройстве защищены следующим образом. Файл локальной базы данных шифруется библиотекой SQLCipher (алгоритм AES-256). Ключевая фраза базы данных – 32 случайных байта – формируется при первом запуске и, как и токены доступа и обновления, хранится в настройках приложения только в зашифрованном виде: шифрование выполняется по алгоритму AES-256-GCM ключом, который создается в защищенном хранилище Android Keystore и не покидает его. База данных и настройки исключены из резервного копирования и переноса данных на другое устройство. Токен доступа передается в заголовке каждого запроса; при ответе сервера с кодом 401 сетевой слой обновляет его по токену обновления и повторяет запрос, а при неудаче завершает сеанс и предлагает выполнить вход повторно. Выпускаемая сборка приложения обменивается данными с сервером только по протоколу HTTPS: передача данных по незащищенному протоколу HTTP разрешена лишь в отладочной сборке. При выходе из учетной записи локальные данные удаляются с устройства.

Уведомления формируются из двух источников. Правила LocalAlerts проверяются на устройстве после каждого изменения данных и в фоновой задаче, поэтому уведомления о приближении к бюджетному лимиту и его превышении, о достижении цели и о предстоящем регулярном платеже формируются и без подключения к сети; каждое событие показывается один раз. Остальные уведомления – о рекомендациях, финансовых рисках, событиях безопасности – формирует сервер; приложение загружает их при синхронизации, а при настроенном сервисе Firebase Cloud Messaging получает также в виде push-уведомлений. Уведомления распределены по каналам Android «Бюджет», «Финансовые цели», «Регулярные платежи», «Рекомендации и прочие уведомления», сохраняются в локальной базе данных и по нажатию открывают соответствующий раздел приложения.
