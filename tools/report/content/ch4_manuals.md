# 4 Руководства администратора и пользователя

## 4.1 Руководство администратора

Руководство предназначено для администратора системы, который разворачивает и сопровождает серверную часть. Оно содержит сведения, предусмотренные п. 9.2.5 ТЗ: действия до установки, порядок установки с указанием возможных проблем, назначение параметров настройки, типовую конфигурацию, порядок резервного копирования и восстановления данных, порядок работы с журналами, мониторингом и моделями машинного обучения.

### 4.1.2 Установка

До установки необходимо выполнить следующие действия:

- подготовить сервер, отвечающий требованиям таблицы {tab:resources}, и установить Docker и Docker Compose;
- зарегистрировать доменное имя и получить сертификат TLS;
- получить дистрибутив серверной части – каталог server репозитория системы;
- определить адреса и учетные данные внешних сервисов, которые будут подключены: почтового сервера, сервиса доставки push-уведомлений, объектного хранилища.

Установка выполняется в следующем порядке:

- скопировать каталог server на сервер и перейти в него;
- создать файл параметров командой «cp .env.example .env» и задать в нем значения, обязательно заменив пароль базы данных POSTGRES_PASSWORD и секретный ключ FH_SECRET_KEY;
- запустить систему командой «docker compose up -d --build»; при первом запуске собирается образ, создается база данных, применяются миграции схемы данных, заполняются справочники валют и системных категорий, обучается начальная версия модели категоризации и загружаются курсы валют;
- убедиться в готовности системы: команда «docker compose ps» должна показывать состояние healthy для контейнеров db, redis, ml и api, а запрос «curl http://localhost:8000/health/ready» – возвращать признак доступности базы данных;
- создать учетную запись администратора командой «docker compose exec api python -m app.manage create-user адрес пароль --role admin»; учетная запись аналитика создается той же командой с ролью analyst либо администратором в мобильном приложении;
- настроить обратный прокси с сертификатом TLS по образцу deploy/nginx.conf.example, чтобы программный интерфейс был доступен только по протоколу HTTPS;
- проверить расписание и каталог резервного копирования и подключить каталог копий к внешнему хранилищу (п. 4.1.4 настоящего руководства);
- при необходимости запустить средства мониторинга командой «docker compose --profile monitoring up -d».

Для стенда и демонстрации тестовые учетные записи с ролями «Пользователь», «Аналитик» и «Администратор» и демонстрационным набором данных создаются командой «docker compose exec api python -m app.manage seed-demo».

### 4.1.3 Настройка

Параметры серверной части задаются в файле .env. Назначение параметров и их значения в типовой конфигурации приведены в таблице {tab:settings}. Изменение параметров вступает в силу после перезапуска командой «docker compose up -d».

!table settings | Параметры настройки серверной части
!widths 5.6,7.4,3.5
!font 10
| Параметр | Назначение | Типовое значение |
| POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB | учетная запись и имя базы данных | finhelper, пароль задается, finhelper |
| FH_SECRET_KEY | секретный ключ подписи токенов доступа | случайная строка не короче 32 символов |

| FH_RATES_TTL_HOURS | срок, после которого курсы считаются устаревшими, часов | 24 |
| FH_PUSH_PROVIDER, FH_FCM_CREDENTIALS_FILE | способ доставки push-уведомлений (log – запись в журнал, fcm – Firebase Cloud Messaging) и файл ключа сервисной учетной записи | log |

| FH_BUDGET_WARNING_PERCENT | порог предупреждения о бюджете по умолчанию, % | 80 |
| FH_DELETED_RETENTION_DAYS | срок хранения удаленных данных, дней | 30 |
| GRAFANA_PASSWORD | пароль администратора Grafana | задается |

Число соединений с базой данных выбирается так, чтобы их сумма по всем процессам не превышала параметр max_connections PostgreSQL (по умолчанию 100) с запасом для резервного копирования и обслуживания: (FH_WEB_WORKERS × число экземпляров серверного приложения + 2) × (FH_DB_POOL_SIZE + FH_DB_MAX_OVERFLOW) < max_connections, где слагаемое 2 учитывает исполнитель фоновых задач и сервис машинного обучения. При превышении этого предела запросы завершаются с кодом 500, а в журнале серверного приложения появляется сообщение «too many clients already».

Для подключения сервиса доставки push-уведомлений необходимо создать проект Firebase, получить файл ключа сервисной учетной записи, разместить его на сервере, указать путь в параметре FH_FCM_CREDENTIALS_FILE, задать FH_PUSH_PROVIDER=fcm и добавить в образ пакет firebase-admin. Параметры проекта Firebase указываются также при сборке мобильного приложения.

Часть настроек изменяется без перезапуска в мобильном приложении, в разделе «Настройки системы» административного модуля: параметры интеграций, порог уведомлений по умолчанию, расписание резервного копирования и режим технического обслуживания. В режиме технического обслуживания синхронизация и онлайн-функции временно недоступны, пользователи видят заданное администратором сообщение, а функции автономного режима продолжают работать (п. 4.1.4.4 ТЗ).

### 4.1.4 Резервное копирование и восстановление данных

Резервное копирование базы данных выполняется автоматически исполнителем фоновых задач (контейнер worker) по расписанию, заданному в разделе «Настройки системы» административного модуля: время запуска указывается в формате cron (минуты и часы, время UTC; по умолчанию ежедневно в 03:00), там же задаются каталог хранения копий (по умолчанию var/backups) и срок хранения (по умолчанию 92 дня, что соответствует трем месяцам по п. 4.3.2.7 ТЗ). Копия создается один раз в сутки в виде файла finhelper_дата_время.dump в собственном сжатом формате PostgreSQL; копии старше срока хранения удаляются. Создание копии отражается в журнале исполнителя фоновых задач.

Копию можно создать вне расписания: запросом администратора POST /api/v1/admin/jobs/backup/run к программному интерфейсу либо командой «docker compose exec worker scripts/backup.sh каталог срок». Каталог резервных копий должен находиться в хранилище, физически отделенном от основного сервера; для этого каталог var/backups подключается к внешнему тому либо копии дополнительно передаются в объектное хранилище.

Восстановление выполняется в следующем порядке:

- включить режим технического обслуживания в разделе «Настройки системы»;
- остановить серверное приложение и исполнитель фоновых задач командой «docker compose stop api worker»;
- восстановить базу данных командой «docker compose run --rm api python -m app.manage restore путь к файлу копии»;
- запустить компоненты командой «docker compose up -d» и убедиться в готовности системы;
- отключить режим технического обслуживания.

После восстановления мобильные приложения пользователей при очередной синхронизации повторно передадут операции, которых нет в восстановленной базе данных, если они еще находятся в очереди устройства.

### 4.1.5 Работа с журналами, мониторингом и моделями

Журнал аудита доступен в мобильном приложении в разделе «Логи» административного модуля. Записи фильтруются по дате, пользователю и типу действия; журнал экспортируется в файл CSV, а внешний журнал может быть загружен из файла CSV того же формата для совместного анализа – такие записи помечаются как импортированные. В журнале фиксируются события входа и выхода, неудачные попытки авторизации, изменения финансовых данных и все административные действия. Журнал ошибок клиентской и серверной частей и журнал синхронизации доступны через программный интерфейс по адресам /api/v1/admin/errors и /api/v1/admin/sync-log.

Раздел «Мониторинг» показывает доступность серверной части по результатам ежеминутных проверок, число запросов, среднее и наибольшее время ответа, число ошибок, состояние компонентов и долю уведомлений, переданных в сервис доставки в течение минуты. Те же показатели в формате Prometheus доступны по адресу /metrics; при запуске с профилем monitoring они собираются сервером Prometheus и отображаются в Grafana (порт 3000). Адрес /metrics не должен быть доступен из внешней сети. Экраны «Логи» и «Мониторинг» показаны на рисунке {fig:admin_logs_screens}.

!figure admin_logs_screens | assets/screens/admin_logs.png | Административный модуль: а – журнал аудита; б – мониторинг | 10.5

Периодические задачи выполняет контейнер worker: проверку работоспособности – каждую минуту, напоминания о регулярных платежах – каждый час, обновление курсов валют и котировок, оценку финансовых рисков, формирование рекомендаций и удаление данных с истекшим сроком хранения – раз в сутки. Любую из задач можно запустить вне расписания запросом POST /api/v1/admin/jobs/имя/run с именем health_check, recurring_reminders или daily, например после восстановления сервера.

Моделями машинного обучения управляет аналитик в разделах «Аналитика ИИ» и «Управление моделями ML». На экране показателей качества отображаются точность, полнота и F1-мера активной модели на контрольной выборке, точность на новых торговых точках, средняя ошибка прогноза расходов и доля положительных оценок рекомендаций. Повторное обучение запускается кнопкой «Запустить новое обучение» и выполняется в фоновом режиме; новая версия становится активной автоматически, если ее точность не ниже значения параметра FH_ML_MIN_ACCURACY, иначе аналитик может выбрать активную версию вручную. Выгрузка файла модели и загрузка его в качестве новой версии в мобильном приложении не предусмотрены и выполняются запросами GET /api/v1/ml/models/{идентификатор}/export и POST /api/v1/ml/models/import программного интерфейса от имени аналитика или администратора. Экраны «Аналитика ИИ» и «Управление моделями ML» показаны на рисунке {fig:admin_ml_screens}.

### 4.1.6 Обновление и удаление

Для обновления необходимо создать резервную копию, заменить содержимое каталога server новой версией и выполнить команду «docker compose up -d --build»; миграции схемы данных применяются автоматически при запуске. Обновление рекомендуется выполнять в период наименьшей нагрузки (п. 4.4.6.3 ТЗ). Мобильное приложение обновляется через магазин приложений.

Для удаления системы необходимо остановить контейнеры командой «docker compose down». Данные при этом сохраняются в томах Docker. Полное удаление вместе с базой данных, файлами и моделями выполняется командой «docker compose down -v», после чего удаляется каталог server и резервные копии, если их хранение не требуется.

| Не выполняются фоновые задачи | не приходят уведомления, не обновляются курсы валют | проверить контейнеры worker и redis, перезапустить их; запустить пропущенные задачи вне расписания |
| Недоступен источник курсов или котировок | в журнале сообщение о недоступности источника | вмешательство не требуется: используются последние сохраненные значения с указанием даты актуальности; при длительной недоступности проверить исходящий доступ |
| Подозрение на несанкционированный доступ | неудачные попытки входа в журнале, обращение пользователя | заблокировать учетную запись, сбросить пароль, изучить журнал аудита по пользователю и адресу, сообщить ответственному за безопасность |
